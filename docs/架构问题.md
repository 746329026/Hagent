## 一、摘要

后端的**分层骨架是成立的**：`controller → app → 能力包（document / retrieval / memory / tool / security）`，且项目自带 `PackagePlacementTest` 对包归属设卡。权限过滤下推到 SQL、双层记忆、幂等入库、穷尽 `switch` 等设计决策，质量明显高于同类项目。

核心缺陷有两个根因：

### 根因一：包边界按「类名后缀」切，而非按「变化的理由」切

这条规则被写进 `WORKING-AGREEMENT.md` 第 12 条规则 5：

> **技术角色与能力域冲突时，跟种类走；没有既定种类时才跟能力域。**

并被 `PackagePlacementTest:99-104` 机械化执行（`*Service → app`、`*Properties → config`）。结果是：

- `app` 变成上帝包（11 文件 / 2,917 行，装 5 类互不相关的东西）
- `config` 变成上帝包（21 文件 / 2,234 行，装装配 + 属性 + 策略选择器）
- 产生 **4 个包级双向环**
- `KnowledgeSearch` 因 `*Service` 后缀被锁进 `app`，而 **`app` 包内零消费者**

### 根因二：「同一规则多出处」与「写了没通电」缺少机制

| 类别 | 现状 |
|---|---|
| 密级字符串 → 枚举的解析 | **3 处**，失败策略互相矛盾（抛异常 / 静默回退 / WARN 回退） |
| 模型可见文本（提示词片段） | **3 处**硬编码，分居 3 个包，靠人工同步 |
| 「实现名」合法值集合 | **3 份**同值副本 |
| 原子文件写 | **3 份**近乎逐字重复 |
| 配置键写了但无效果 | **9 个键** |
| 零调用者的公开成员 | **约 20 个** |

> **一句话结论**：设计判断的水平领先于物理布局的纪律。

## 二、总体评价

### 2.1 值得肯定的设计

| # | 设计 | 证据 | 价值 |
|---|---|---|---|
| 1 | 权限规则单一出处 | `AccessLevel.visibleLevels` 由 `visibleTo` **派生**（`AccessLevel.java:118-122`），"逐篇判定"与"SQL 过滤"不可能给出不同答案 | 安全规则不会双写漂移 |
| 2 | 端口按语义分层而非按存储分层 | `record`（权威）/ `context`（可丢）/ `session`（元数据）/ `longterm`（跨会话）四端口；`ConversationRecordStore.java:9-63` 用表格论证"两个角色需求相反" | 本项目最有价值的架构结论 |
| 3 | 失败分级而非一刀切降级 | `LayeredConversationMemory`：记录层失败 ERROR、上下文层失败 WARN、旁路（审计/目录）失败只 WARN | 关键路径与非关键路径分离 |
| 4 | 幂等入库用双哈希且理由充分 | `HashingSupport.java:11-34`：`docHash` 决定整篇跳过、`contentHash` 决定块级比对；并论证"改密级必须触发重新入库" | 避免"权限调整静默失效" |
| 5 | 穷尽 `switch` 且刻意不写 `default` | `MemoryMode.wireName:136-141`、`AgentPipeline.budgetOf:862-871` | 新增模式编译失败而非运行期 NPE |
| 6 | 配置写错启动即失败 | `MemoryConfigValidator`（`EnvironmentPostProcessor`）、`RetrievalProperties.afterPropertiesSet:154-193`、`VectorStoreConfig.vectorTableSelfCheck` | 不静默降级 |
| 7 | `tool → document` 依赖为 **0** | 检索工具只认 `retrieval.RetrievedChunk` | 边界划得比多数项目准 |
| 8 | `document` 是零外部 hagent 依赖的叶包 | 全量 grep 证实 | 可独立演进 |

### 2.2 核心缺陷总览

## 四、缺陷清单

### 4.1 P0 — 正确性 / 安全 / 静默失效（8 条）

#### P0-1 密级字符串三处解析、三种失败策略 ★最严重

| 路径 | 脏数据（如 `level: 绝密`）的处理 |
|---|---|
| 入库 `AccessLevel.parse:134-146` | **抛异常** |
| 检索 `RetrievedChunk:98-138` | **静默回退 `DEFAULT`（=INTERNAL）** |
| 长期记忆 `FileLongTermMemoryStore:427-435` | **WARN + 回退** |

- **根因**：`DocumentMetadata` 只有 `toMap:168-183`，**无 `from(Map)`**，于是 `RetrievedChunk` 另写了第二套 metadata→字段解析。
- **影响**："越权是否被拦住"取决于哪条路径先碰到脏数据；与 2.1-① 精心保证的"单一出处"直接冲突。
- **建议**：加 `DocumentMetadata.from(Map)` 作读侧唯一入口，三处统一为"拒绝入库 / 拒绝使用"。**优先级高于任何搬包动作。**

#### P0-2 模型可见文本三处硬编码

| 位置 | 内容 | 人工同步对象 |
|---|---|---|

## 五、命名规范评估

### 5.1 名不副实

| 名称 | 实际是什么 | 建议 |
|---|---|---|
| `HashingSupport.contentFingerprint()` | 内部先 CRLF 归一化 + `strip()`（`:81-86`），**不是裸 SHA-256** | `contentFingerprint` |
| `MemoryMode` | **预算档位**（`:49-52` 自承"唯一作用是选择记忆预算"） | `MemoryBudgetProfile` |
| `ReasoningTrace` | 名词名、动词行为（静态 `render` / `parse`） | `ReasoningTraceCodec` |
| `LayerStatus` | 名字像枚举，实为 DTO；两字段是裸 `String`，在 5 个实现的 `probe()` 里共 **12 处**硬编码字面量 | `MemoryLayer` / `MemoryBackend` 枚举 |
| `ConversationRepository` | 会话**元数据仓储**（可写），不是静态清单 | `ConversationRepository`（可选） |
| `ToolContextSupport` | 名字不说明职责：它是**键名契约 + 身份解析策略**，且被 `app` 层**写**、`tool` 层读 | `ToolContextKeys` + `ToolContexts` |
| `DocumentKind` | 实为"种类 → 策略"映射表（构造器 `(displayName, chunkingStrategy, defaultLevel)`） | 名可保留（设计正确），但类头须一句话说明 |

### 5.2 同义异名（同一概念多名字）

| 概念 | 并存的叫法 |
|---|---|
| 会话 | `Conversation*`（类）/ `session`（HTTP 路径、`SessionDtos`、包名 `memory.session`）/ `catalog`（`ConversationRepository`）/ `chat_conversation`（表） |
| 模式 | `CONVERSATION`（枚举）/ `chat`（配置键、HTTP）/ `Conversation*` |
| 读 | `load`（门面）/ `readLatest`（记录层）/ `get`（缓存层） |
| 删 | `clear` / `delete` / `evict` —— 而 4 个实现里 `clear ≡ delete` |
| 入库结论 | `IngestOutcome` + `IngestResult` + `SaveResult`（memory 侧，枚举也叫 `*Result`） |
| 切分块 | `document.Chunk`（`index/total/section/text`）vs `retrieval.RetrievedChunk`（`content/source/level/similarity/band`） |
| 检索服务 | `app.KnowledgeSearch` vs `tool.KnowledgeRetrievalTool` |
| 思考分段 | `ReasoningTrace.Section` vs `SessionDtos.ReasoningSection`（字段完全一致） |
| 文本 ↔ 结构 | `MessageCodec`（Codec 后缀）vs `ReasoningTrace`（Trace 后缀）—— 同一类工作 |

### 5.3 不同义同名

- `*Store` 三义：权威存储 / 领域服务（`LongTermMemoryStore` 含授权 + 限额 + 渲染）/ 健康探针（`probe()`）。
- `*Cache` 两义：可丢副本，但 `get` 返回 `null` 表示未命中，**与包内"绝不返回 null"的立场相反**（`ConversationRecordStore.readLatest:83`）—— 同包两套 null 契约。

### 5.4 后缀问题

- `*Support` 共 4 个（`ToolContextSupport` / `SseSupport` / `HashingSupport` / `ChunkingSupport`）：**后缀不承载任何职责信息**，与第 12 条规则 3（"后缀必须承载种类语义"）冲突。
- 值得肯定：`memory` 包内**没有** `*Support` / `*Helper` / `*Manager`。
- `File*` / `Mysql*` / `Redis*` / `NoOp*` 现在正确，但移入 `impl.*` 后会三重冗余（`impl.file.FileConversationRecordStore`），应同步去前缀。
- `package memory.record` + `ConversationRecordStore` → 全限定名两次 `record`，而 `record` 是 Java 21 受限标识符。

### 5.5 判定

命名整体**表达意图清楚、术语有文档**（`WORKING-AGREEMENT` 有术语表），但存在系统性的「**文档债务代替命名债务**」：`ConversationMemory` 151 行中 87% 是注释，用 40 行表格才讲清"三个接口的读方法为何不同名"，同一段论证又在 `ConversationRecordStore:51-63`、`ConversationContextCache:31-47` 各抄一遍。

> **当一段命名需要三份文档来解释时，该改的是名字。**

### 执行顺序的理由

1. **第 1 批解决"现在就在错"的问题** —— 不是风格问题，而是静默失效与安全缺陷。
2. **第 2 批建立"唯一出处"** —— 在此之前搬包，会把同一份重复逻辑搬两次。
3. **解环必须排在拆包之前** —— 新工具族落地时，依赖方向不能靠"学上一个类的写法"猜。
4. **重构排最后** —— 前 3 批会大幅缩小它的范围。

## 八、守卫机制升级

现有 `PackagePlacementTest` 按**类名后缀**设卡，它正是 `KnowledgeSearch` 被锁进 `app` 的直接原因。建议换成 ArchUnit，规则从"后缀"改为"层 + 域"：

```java
@ArchTest static final ArchRule 分层方向 = layeredArchitecture()
    .layer("api").definedBy("..api..")
    .layer("app").definedBy("..app..")
    .layer("agent").definedBy("..agent..")
    .layer("domain").definedBy("..retrieval..", "..document..", "..memory..", "..conversation..")
    .layer("infra").definedBy("..config..", "..common..", "..observability..")
    .whereLayer("infra").mayOnlyBeAccessedByLayers("app");   // ★ 锁死 domain → config

@ArchTest static final ArchRule 无环 =
    slices().matching("com.hagent.(*)..").should().beFreeOfCycles();

@ArchTest static final ArchRule 端口实现分离 =
    classes().that().implement("..*Store").or().implement("..*Catalog")
        .should().resideInAnyPackage("..impl..");

@ArchTest static final ArchRule tool不依赖app =
    noClasses().that().resideInAPackage("..tool..")
        .should().dependOnClassesThat().resideInAPackage("..app..");
```

两条关键说明：

1. **`domain` 不得依赖 `config`** —— 这一条能一次性锁死 3 个环的回归。
2. 必须用**字节码级**检查（ArchUnit 是），不能用手写 import 扫描 —— 否则 `KnowledgeRetrievalTool:204/206` 这类全限定名写法会漏掉 2/3 的边（这正是踩坑 #40 的同类盲区）。

## 九、结论与下一步

### 结论

1. **架构分层方向正确**。`controller → app → 能力包`的骨架、权限下推、双层记忆、穷尽 `switch` 等决策质量高。
2. **主要缺陷源于一条过于教条的规则**：`WORKING-AGREEMENT` 第 12 条规则 5「技术角色与能力域冲突时跟种类走」，被机械化执行成"按后缀定归属"，直接制造了 2 个上帝包与 4 个包级环。
3. **第二类缺陷是机制缺失**。项目对"设计论证"极其严谨（文档里能查到每条决策的理由），但缺少"接线校验"—— 同一规则允许有 3 份出处，配置键可以写而无效，公开方法可以零调用者。这类问题**全部不会报错**，正是项目自己在第 7、12、13 条反复要防的。
4. **最高性价比的动作不是重构，而是删除与收敛**。第 1 + 第 2 批能消除全部已知静默失效、1 个安全缺陷、约 20 个死成员、5 组重复实现，且不改任何结构。

### 下一步建议

从第 1 批的 `DocumentMetadata.from(Map)`（P0-1）开始 —— 它同时是安全缺陷、重复出处、以及 5 个零测试规则类的入口。
