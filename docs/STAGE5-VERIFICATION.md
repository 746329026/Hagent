## 五、验证 ChatMemoryAdapter 的预算装配

**为什么必须验**：这是"上下文窗口预算"这条约束在**框架边界**上的闸门。
框架的 `ChatMemory.get(String)` **没有预算参数** —— 如果不在这里绑一个已配置的预算，
将来接框架组件时会变成**无界读取历史**，成本失控且没有任何报错。

在本阶段它**还不在主链路上**（主链路的记忆由 `ConversationMemoryAdvisor` 直接调 `ConversationMemory`），
所以**只能靠启动日志验证它按模式各自绑了正确的配置**。

### 6.1 看启动日志

启动后，在日志里搜索 `适配器已就绪`：

```powershell
# 若用 IDEA 启动，直接在控制台搜 "适配器已就绪"
# 若日志落到文件：
Select-String -Path "<你的日志文件>" -Pattern "适配器已就绪" | ForEach-Object { $_.Line.Trim() }
```

- **预期结果**（一字不差地出现两组、且数值分别对应两组配置）：

  ```
  [记忆] 适配器已就绪（框架边界的预算闸门）：delegate=FileConversationMemory
        模式预算={CONVERSATION=TokenBudget[maxTokens=5000, maxMessages=30],
                  WORKFLOW=TokenBudget[maxTokens=50000, maxMessages=200]}
  ```

  > ★ **键的顺序现在是稳定的**（`CONVERSATION` 在前、`WORKFLOW` 在后）——
  > 阶段 6 后半把内部实现从 `Map.of(...)`（迭代顺序不保证）
  > 换成了 `LinkedHashMap` + `com.hagent.memory.MemoryBudgets`，顺序按 `MemoryMode` 的声明顺序。
  > **原文那条"两个键的顺序可能颠倒，不要当成异常"的提醒已作废** ——
  > 现在顺序颠倒反而是异常信号。

- **判定要点**（三条都要满足）：
  1. `delegate` = 当前 `type` 对应的实现（`type: file` 时是 `FileConversationMemory`）
  2. `CONVERSATION` 的数字 = `application.yml` 里的 `conversation-max-tokens` / `conversation-max-messages`

## 附：三条必须知道的限制（不是 bug，是设计决定）

1. **流式端点里只有 `/stream-sse` 带记忆。**
   `/stream` 和 `/stream-flux` **刻意不带** —— 它们是"流式机制对照实验"，加记忆会污染对照。
   所以想测记忆，请用 `POST /chat`（同步）或 `POST /stream-sse`。

2. **模型调用失败时，记忆里不会留记录。**
   这是"先调模型、后写入"的设计使然 —— 避免留下"有问无答"的半截记录。
   所以用假 key 测试时，记忆目录**必然是空的**，这不是故障。

3. **本清单第 2.4 步是唯一能证明"记忆注入真的生效"的测试，务必跑它。**
   其他步骤只能证明"记忆能装配、能落盘"—— 那是**写入端**。
   只有 2.4（下一轮答出名字）能证明**读取端**真的把历史注入了 prompt、且模型用上了。
   两者是独立的失败点：写入成功但注入失败时，文件看着完全正常。
