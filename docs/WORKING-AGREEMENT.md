# Hagent 协作协议（Working Agreement）

> 本文件记录本项目在"人 + AI 教练"协作模式下必须遵守的流程与格式约定。
> 目的：**保证每个阶段的产出都是"本人理解并拍板的设计"，而不是 AI 单方面代劳的代码。**

---

## 1. 每个阶段的推进流程（硬约束）

推进任何一个阶段，都必须按下面五步走，**未获得本人明确放行（回复 OK）之前，不写任何代码**。

| 步骤 | 教练做 | 本人做 |
|---|---|---|
| ① | 讲清"这个阶段解决什么问题、涉及哪些概念" | 阅读、提问直到理解 |
| ② | 提出**需要本人判断的设计问题** | 给出自己的答案（可以答错、可以说不知道） |
| ③ | 纠正错误、补充遗漏，确认理解到位 | 修正、复述关键点 |
| ④ | —— | **明确放行（OK）** |
| ⑤ | **开始写代码** | —— |

### 为什么要有这条

- 项目最大的价值不是"代码能跑"，而是**本人能讲清每一处设计决策**。
- 如果代码先写好、概念后补，本人在讲设计时只能复述结论，答不出"为什么这么做"。
- 反面教训：本项目在"三种流式方式"和"结构化输出字段选择"两处，教练曾直接写代码 / 直接要答案，跳过了概念讲解。此后修正。

---

## 2. 每次代码改动后的汇报格式（固定六段）

写完代码并编译通过后，必须按下面顺序汇报：

```
【本次改动文件】
  - 新增：<路径> —— 类 / 方法 / 作用
  - 修改：<路径> —— 改了哪部分、为什么改
  - 删除：<路径> —— 为什么删

【建议阅读顺序】
  - 给出一条"从哪读起"的顺序，而不是把文件平铺一遍
  - 顺序遵循：先契约 → 再结构 → 再难点 → 再装配 → 最后测试
  - 每一项写清【读的时候看什么】：哪个注释块、哪个方法、哪条断言
    （例："先读它的类注释 —— 两个角色的需求对照表在那里"）
  - 最后标一句"只有一个小时的话，读哪三处"

【编译与测试】
  - 实际结果（命令 + 输出）

【本阶段代码的数据流向】
  - 一张流程图：数据从哪个层进来、经过哪些层、到哪层出去
  - 一张思维导图：本阶段核心对象与其职责的结构化拆解
  - 这两张图同时同步写入 docs/PROCEDURES.md【该阶段小节的开头】

【为后续阶段准备了什么】
  - 本次写的哪些内容，后面哪个阶段会直接消费

【需要本人决策的事】
  - 列出待拍板的点（若无则写"无"）
```

### 为什么要有"建议阅读顺序"这一条

**代码清单回答"改了哪些文件"，阅读顺序回答"从哪读起" —— 后者才决定能不能读懂。**

- 一次结构性改动往往二三十个文件。平铺清单等于把"找入口"这件事丢给读者，
  而**找入口恰恰是最难的一步**：新人打开 `git diff` 看到 40 个文件，第一反应是"从哪开始"。
- **顺序本身就是设计的一部分。** "先读接口再读实现"不是习惯问题 ——
  本项目把"为什么这么设计"写进了**接口的类注释**
  （例：`ConversationRecordStore` 的类注释里是"两个角色的需求对照表"）。
  顺序错了，读者会先陷进实现细节，再回头补"为什么"，等于读两遍。
- 它还逼教练做一次自查：**如果一条清晰的阅读顺序说不出来，说明这次改动的结构是乱的。**
  （"把 40 个文件平铺"和"给出顺序"之间的差距，就是"改动是否有主线"的差距。）

### 为什么要有"数据流向图"这一条

- 代码跑通 ≠ 理解链路。**能画出"数据从哪来到哪去"，才算真正掌握了这一层。**
- 面试常问"你这个请求从进来到返回经过了哪些层"——有图就有答案。
- 图放在 `PROCEDURES.md` 每个阶段的**开头**：打开文档先看到整段链路，再看细节。
- 本人在动手复查代码、或在脑子里复述链路时，图是最省力的抓手。

### 画图要求

- 用 **Mermaid**（GitHub 与 IDEA 都能直接渲染），不贴图片文件。
- 至少包含 **入口层 → 中间处理层 → 出口层**，并标注每层做了什么。
- 若本阶段引入了**两条并行路径**（例如结构化输出的"schema 通道"与"提示词通道"），
  必须把两条都画出来——**差异靠图才看得清**。

### 为什么要有这条（汇报格式）

- "改了哪些文件"是本人复查代码的入口；
- "为后续准备什么"能避免**备而不用**（本项目已清理过多次这类问题：JPA 死配置、jsoup 依赖、未使用的事件定义）；
- 把决策点放到最后统一列出，避免埋在长段落里被漏掉。

## 3. 验证原则

- **结论必须有证据**，禁止"应该是这样"。证据形式：日志、SQL 直查、原始字节、字节码、真实 HTTP 往返。
- **加验证项时要同时确认两件事**：① 数据确实发出去了；② 观察者能看到它。
  - 反面教训：曾断言"你应该能看到 retry 字段"，实际浏览器 EventSource 面板不展示帧级字段——把"发出去了"误当成"能看到"。
- **教练的断言同样需要验证**。反面教训：教练曾断言"删掉注解处理器配置会导致编译失败"，实测只是警告。
- 对第三方 API 的用法，先读它的真实签名（javap / 配置元数据 / 官方文档），**不凭记忆写**。

---

## 4. 代码归属约定

- 机器杂活（Docker 操作、依赖版本核查、镜像拉取、环境排障）由教练完成，不进本人学习范围。
- **业务设计、技术选型取舍、核心抽象、异常策略必须由本人拍板**。
- 关键代码由教练执笔，但**每个决策点必须先经本人确认**；本人需要能独立复述设计理由。

---

## 5. 文档即作品

- `docs/PROCEDURES.md` 按阶段记录：本阶段目标 / 为什么做 / 主要新增涉及文件 / 踩坑记录 / 阶段结果。
- 踩坑记录只保留**有可迁移认知的大坑**（现象 / 原因 / 处理方式 / 收获），一次性报错不再逐条记录。
- 本文件与 `PROCEDURES.md` 都提交进仓库——面试时是"工程化意识"的直接证据。
- ★ **不为每个阶段单独写"验收清单"文档**（原 `STAGE*-VERIFICATION.md` 的做法已停）：
  验收清单**在对话里给**（本人照着跑）；其中**必须留到下一个对话的部分**
  （待跑项 + 判定标准）压进 `HANDOFF` 的待办里。

  **为什么**：验收清单是**一次性**的（跑完就过期），而 `docs/` 里该留的是**长期有效**的东西
  （设计理由 / 踩坑 / 决策）。一份跑完就没用的清单会稀释 `docs/` 的信噪比。

  **前提是"不能丢"**：清单里的**待跑项**必须进 `HANDOFF` ——
  因为**新对话看不到旧对话的消息**，只留在对话里等于丢掉。

  **已存在的 `STAGE5-VERIFICATION.md` / `STAGE6-VERIFICATION.md` 保留**：
  它们是**已跑过的真实证据快照**（含实测日志），删掉等于删证据。

## 6. 同一个操作性错误重复出现必须机制化

**规则**：当同一个操作性错误（配置没设、端口被占、命令写错等）在协作过程中出现 **≥2 次**时，
必须把它从"每次口头提醒"升级为**机制化解决**，而不是继续提醒。

**机制化的可选手段**：

| 手段 | 例子 |
|---|---|
| 改配置默认值 | 把需要人工填的占位符改成带明确提示的默认值 |
| 加启动自检 | 启动探针里显式报出"哪一项没配、怎么配" |
| 固化操作入口 | 把多行命令写成一个脚本 / IDEA 运行配置 |
| 写进文档 | 在 `PROCEDURES.md` 的踩坑记录里留档 |

**为什么要有这条**：
重复提醒等于把"人会忘"这个事实当作不存在 —— 而工程化要解决的**正是这件事**。
本项目已出现过同一错误重复 5 次（DeepSeek API Key 未生效），根因始终是
"配置来源不唯一"（IDEA 的"运行当前文件"不带环境变量，而运行配置带），
靠提醒无法解决，必须机制化。

## 7. 每一步都必须能说清"它解决什么问题"，警惕画蛇添足（硬约束）

**规则**：在动手实现任何一层之前（无论是新建类、新建切面、还是新建一个模型调用），
必须先回答三个问题，且答案要写进 `PROCEDURES.md`：

| # | 问题 | 不合格的答案 |
|---|---|---|
| ① | **它解决什么具体问题？** | "业界都这么做"、"框架支持这个能力"、"以后可能有用" |
| ② | **它的产出谁消费？** | "会存下来"、"给下游用"（说不出具体哪个类 / 哪个阶段） |
| ③ | **不做它会怎样？** | "不够完整"、"不够工程化"（说不出具体的功能缺失或风险） |

**任何一项答不出来，就不做。**

### 为什么要有这条

本项目在"任务意图提取层"（intent）上完整地踩过这个坑，代价是**一整层代码被删除**：

- 它的构想是"先让模型解析出结构化任务意图，再由代码据此决定调哪些工具"
- 听起来完全合理 —— 但**说不出它的产出谁消费**：`ChatAppService` 根本不读那个 intent
- 更糟的是它**和模型自己的工具调用在重复同一个判断**：给模型看"用户的话 + 交付物枚举"问它该产什么，
  又给模型看"用户的话 + 工具 JSON Schema"问它该调哪个工具 —— 同一判断做两遍
- 直到追问"intent 的结果落到哪里、谁读它"时，才发现**这个问题本身无法回答**

**这条规则要防的不是"写错代码"，而是"写了一层根本不该存在的代码"。**
后者更贵：代码能编译、测试能过、架构图很好看，但它是纯粹的复杂度。

### 具体的警戒信号（出现即停下来重新论证）

| 信号 | 为什么危险 |
|---|---|
| 产出的东西"以后会被用到" | 没有消费方的产出必然是死代码，且会误导后来人以为它在主链路上 |
| 让模型做两遍同一个判断 | 两遍判断会产生两个答案，且必然不一致；还会引入一对需要手工同步的字典 |
| 为了实现它而引入"两个组件约定不互相干涉" | 靠约定维持的隔离会被人改坏；能靠结构隔离就别靠约定 |
| 新建的抽象还没有第二个实现 / 第二个使用者 | 一个实现之上加抽象层是纯开销 |
| 需要在注释里反复解释"它其实不参与主流程" | 注释在替设计道歉，说明设计有问题 |

### 与第 ⑥ 条的关系

第 ⑥ 条管的是"**同一个错误重复出现**"（操作性错误），
第 ⑦ 条管的是"**第一次就把不该做的东西做出来**"（设计性错误）。
两者都是把问题从"靠人记得"升级为"靠机制拦住"：
⑥ 靠自动化手段，⑦ 靠**动手前的三问**。

## 8. 文档小节编号：禁止手工改数字，必须脚本化重排

**规则**：往文档中间**插入或删除**章节后，**不许手工去改后续小节的中文数字编号**，
必须用脚本按出现顺序**整体重排**，并校验"正文里引用的编号/锚点"与"真实标题"一致。

**为什么要有这条**：本项目已出现 **2 次**同类错误，两次都是"往中间插章节"引起的：

| 次数 | 位置 | 表现 |
|---|---|---|
| 1 | `docs/PROCEDURES.md` | 新增阶段 5 小节后，其内部小标题写成 `5.4` 却缺 `5.3` |
| 2 | `docs/STAGE5-VERIFICATION.md` | 插入"核心 6 项"小节后，二级标题从 `三` 直接跳到 `五`，且缺 `四` |

**为什么手工改一定会错**：手工改是"局部修补"——
你只改了眼前看见的那几个数字，而编号是**全局有序属性**，插入一个就影响后面所有项。
更隐蔽的是**正文里的交叉引用**（"见第 4 节"、`[四](#四...)`）**不会跟着变**，
于是文档读起来是对的、点进去是错的。

**脚本化的做法**（本次实际采用）：

```powershell
# 按文档顺序扫描二级标题，用中文数字序列整体重排
$cn = @('零','一','二','三','四','五','六','七','八','九','十')
$seq = 0
$lines = [System.IO.File]::ReadAllLines($p, [System.Text.Encoding]::UTF8)
$out = foreach ($line in $lines) {
  if ($line -match '^##\s+[零一二三四五六七八九十]、(.+)$') { "## $($cn[$seq++])、$($Matches[1])" }
  else { $line }
}
```

**改完必须校验两件事**（缺一不可）：

1. **编号连续**：`零、一、二、三…` 无跳号、无重号
2. **锚点有效**：正文里每个 `[文字](#锚点)` 都能对应到一个真实标题
   （校验时注意 GitHub 锚点规则：**转小写、空格→`-`、标点与反引号会被剥掉**。
   本次就栽在这一条上 —— 标题里的 `` `ChatMemoryAdapter` `` 反引号被剥掉，
   而引用里带着反引号，于是链接失效）

**这条属于第 ⑥ 条的实例**：同一操作性错误重复 ≥2 次 → 从"下次注意"升级为"固定做法"。

## 9. 编码约定：中文必须全链路 UTF-8（跨阶段硬约束）

**背景**：本项目的核心业务是**处理中文办公文本**。而编码错误的特征是 ——
**HTTP 200、请求成功、没有异常、没有日志**，唯独内容是错的。
它是"静默数据损坏"里最典型的一类，比崩溃危险得多。

**所以编码不是"细节"，是必须写进约定的工程约束。**

### 9.1 参考实现：客户端侧的编码陷阱（已踩过）

PowerShell 5.1 的 `Invoke-WebRequest` 传字符串 body 时**不会自动按 UTF-8 编码**：

```powershell
Invoke-WebRequest -Body '{"message":"我叫张三"}'    # ❌ 服务端收到 ????????
```

原因：`Content-Type` 没带 `charset` 时它用 ISO-8859-1 编码，而该编码表里没有中文字符，
于是**逐字符替换成 `?`（ASCII 63）**。

**症状极具误导性**：服务端一切正常、探针全绿、HTTP 200，
只有模型的回答是"你的消息出现了乱码"——极易误判成"模型中文支持有问题"。

**处置（已机制化）**：项目提供 `tools/hagent-test.ps1`，其中的命令把请求体
**显式编码为 UTF-8 字节**再发送。做任何手工测试都用它，不要裸写 `Invoke-WebRequest`。

```powershell
. "C:\Users\Rong\Desktop\实习准备\Hagent\tools\hagent-test.ps1"
问 -Message "我叫张三，在一家做企业服务的公司上班"
```

> ⚠️ 该脚本**必须保存为带 BOM 的 UTF-8**。PowerShell 5.1 读取无 BOM 文件时按本地代码页
> （GBK/936）解释，中文函数名会乱码到语法错误、脚本直接无法加载。
> **注意这与 Java 源码的规则相反**：`.java` 要无 BOM，`.ps1` 必须有 BOM。
> 另外：用编辑器/工具重写该文件会**剥掉 BOM**，改完必须复查前 3 字节是否 `239,187,191`。

### 9.2 当前已在正确状态（**不要重复处理**）

| 层 | 状态 | 依据 |
|---|---|---|
| JVM | ✅ `file.encoding = UTF-8` | JDK 18+ 默认 UTF-8，**不受 Windows 代码页影响** |
| 请求进（JSON body） | ✅ 中文正确解析 | 实测：`Content-Type` 带不带 `charset` 都对 |
| 响应出（JSON） | ⚠️ **字节正确，但客户端会解错** | 服务端发的**原始字节**确实是标准 UTF-8（实测）。但响应头 `application/json` **不带 charset**，而 PowerShell 的 `Invoke-WebRequest` 在缺 charset 时**按 ISO-8859-1 解码响应体** → `$resp.Content` 里中文是乱码。★ 见下方 **9.2.1** —— 这是"发出去了 ≠ 能看到"的**第二个实例** |
| 响应出（SSE） | ✅ 中文完好 | 实测字节 `E5 AD A3`（标准 UTF-8 三字节/字） |
| 文件（会话记忆） | ✅ 已显式 | `FileConversationMemory` 的读写均传 `StandardCharsets.UTF_8` |
| 构建 | ✅ 已显式 | `project.build.sourceEncoding=UTF-8` |

### 9.2.1 ★★ 响应方向的同款陷阱：`Invoke-WebRequest.Content` 会按 ISO-8859-1 解码

**9.1 讲的是【发送】方向；【接收】方向有同一个默认值，长期没被发现。**

```text
服务端响应头： application/json          ← ★ 没有 charset（实测）
PowerShell 的 Invoke-WebRequest 在缺 charset 时按 ISO-8859-1 解码响应体
→ $resp.Content / $resp.ParsedHtml 里的中文全是乱码
```

**实测证据**（阶段 6 验收，同一份 **125 字节**的响应体，两种读法）：

| 读法 | 结果 |
|---|---|
| `$resp.Content \| ConvertFrom-Json` | `æ ¹æ®ãåå·¥æå...` ❌ |
| `UTF8.GetString($resp.RawContentStream 的字节)` | `根据《员工手册》第二章…` ✅ |

**为什么长期没被发现**：`tools/hagent-test.ps1` 自己的注释写着
"要确认发送是否正确，**看服务端日志**的 `[PromptTraceAdvisor] → 请求 | 内容=...`" ——
**所有人工验证都是看服务端日志做的，没人去读脚本返回的「回复」字段**。
而"响应出（JSON）✅ 中文完好"这个结论是**对原始字节**验的（用 `TcpClient` 之类），
**没验过"观察者能不能看到"**。

> ★ 这正是本协议第 3 条自己记录过的那条教训：
> "曾断言'你应该能看到 retry 字段'，实际浏览器 EventSource 面板不展示帧级字段 ——
> **把「发出去了」误当成「能看到」**"。同一个错误，换了一层又犯一次。

**处置（已做）**：`tools/hagent-test.ps1` 里所有读响应的地方改为
**取原始字节 → 显式 `UTF8.GetString`**，收口到两个函数
`读响应体` / `读错误响应体`（含失败响应 4xx/5xx 的错误信息，同样会乱码）。

**写测试/排查代码时的做法（以后照这个来）**：

```powershell
# ✅ 成功响应
$ms = New-Object System.IO.MemoryStream
$resp.RawContentStream.Position = 0
$resp.RawContentStream.CopyTo($ms)
$body = [System.Text.Encoding]::UTF8.GetString($ms.ToArray())

# ✅ 失败响应（4xx/5xx）—— 异常路径拿不到响应对象，只有流
$stream = $_.Exception.Response.GetResponseStream()
$ms = New-Object System.IO.MemoryStream
$stream.CopyTo($ms)
$body = [System.Text.Encoding]::UTF8.GetString($ms.ToArray())

# ❌ 不要用：$resp.Content（会按 ISO-8859-1 解码）
# ❌ 不要用：New-Object System.IO.StreamReader($stream)（默认编码不可控）
```

**⚠️ 不要为了这个去给响应加 `charset=UTF-8`**：那属于"改服务端去迁就一个客户端 bug"，
而且会新增一处需要同步的配置（本协议一贯反对）。**问题在客户端解码，就在客户端解决。**

**❌ 明确不需要做的（避免画蛇添足）**：

- **不加** `CharacterEncodingFilter` —— Spring Boot 已自动装配
- **不加** `produces = "...;charset=UTF-8"` —— 实测不加也是 UTF-8，加了只是多一处要同步的配置
- **不改** `StringHttpMessageConverter` —— 已由 `spring.http.converters.string-encoding-charset` 覆盖
- **不管** `sun.jnu.encoding` / `stdout.encoding = GBK` —— 前者影响文件路径代码页（我们都是 ASCII 路径），
  后者只影响**控制台显示**（日志文件里的字节仍是 UTF-8）

### 9.3 ★ 一个必须记住的"两层默认值"

排查 SSE 中文时我一度怀疑会坏，因为：

```
Spring Framework 的 StringHttpMessageConverter.DEFAULT_CHARSET = ISO_8859_1   （字节码实证，7.0.9 依然如此）
```

但**实测中文是好的**。根因是 **Spring Boot 覆盖了它**：

```
Spring Boot 4.1.1 的 StringHttpMessageConvertersCustomizer：
    new StringHttpMessageConverter(properties.getStringEncodingCharset())

配置项：spring.http.converters.string-encoding-charset   默认值 = UTF-8
```

**教训**：**「框架的默认值」和「你在用的那个发行版的默认值」是两件事。**
判断编码问题必须用**真实字节**验证（或查实际生效的配置项），
不能根据"我记得这个类的默认值是 ISO-8859-1"下结论。

### 9.4 ★ 后续阶段**必须显式做**的四处（其中两处不可逆）

| # | 阶段 | 位置 | 必须做什么 | 不做的后果 |
|---|---|---|---|---|
| **1** | 7 | **MySQL 建库/建表** | `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` | 用 `utf8`（3 字节）**存不下 4 字节字符**（emoji、部分生僻字与中文标点）→ **插入时截断或报错** |
| **2** | 7 | **JDBC URL** | `?characterEncoding=utf8&useUnicode=true` | 驱动按服务端协商编码走，中文可能变 `?` |
| **3** | 12 | **`.md` 长期记忆** | `Files.readString/writeString(..., UTF_8)` | Windows 默认 **GBK**，换台机器读同一份记忆就乱码 |
| **4** | 7+ | **CSV / 文本导出** | 显式 UTF-8 **+ BOM** | Excel 打开 UTF-8 CSV 会乱码（Excel 靠 BOM 判断编码） |

> **为什么 1 和 2 是"必须"而非"建议"**：MySQL 的字符集在**建表时定死**，
> 事后改要 `ALTER TABLE ... CONVERT TO`，而**已写入的数据可能已被截断、无法恢复**。
> 这是**不可逆**的，所以必须在写 DDL 之前定好。

### 9.5 排查编码问题的方法（不要靠猜）

1. **看真实字节**，不看"应该是什么" —— 用 `TcpClient` 抓原始响应，或看服务端日志的原始内容
2. **查实际生效的配置项**，不查"类的默认值"（见 9.3）
3. **定位是哪一侧的问题**：客户端编码 vs 服务端解码 vs 存储编码 —— 三者独立
4. 一个快速判据：**中文在 UTF-8 下是 3 字节/字**。若响应字节数 ≈ 字符数，说明已经退化成单字节编码

## 10. 切面必须考虑"内层被重复调用"，可重复的用幂等处理

**规则**：新增或修改任何 Advisor 时，**必须先判断它会被调用几次**。
若存在"一次请求内被调用多次"的可能，**其副作用必须做成幂等的**。

### 为什么会有重复调用（机制，不是偶发）

框架的 `ToolCallingAdvisor` 的 `order = Integer.MIN_VALUE + 300`，位于切面链的**最外层**，
它自带**工具调用循环**：模型每要求调一次工具，它就**再次调用整条内层链**。

```
ToolCallingAdvisor（最外层，自带循环）
  └─ 内层链：RAG 切面 → 日志切面 → 记忆切面 → 模型
       ↑
       这一整段会被【重复执行 N 次】，N = 工具调用轮数
```

所以：**只要一个切面挂在 `ToolCallingAdvisor` 内层，它的 `adviseCall` / `before` 就会被跑 N 次。**
这不是异常情况，而是正常的多步 Agent 执行路径。

### 框架自己就在防这件事（有据可查）

反编译 `MessageChatMemoryAdvisor.before()` 可以看到它专门做了一次重复检查：

```java
if (!isMemoryAlreadyInPrompt(instructions, memoryMessages)) {
    messages.addAll(memoryMessages);      // 已在 prompt 里就不再注入
}
messages.addAll(instructions);
```

**框架需要这个检查，正是因为它知道 `before()` 会被调用多次。** 这是本项目该遵循的同一模式。

### 怎么做到幂等（按副作用类型选手段）

| 副作用类型 | 幂等做法 | 例子 |
|---|---|---|
| **只读但昂贵**（检索、embedding、远程调用） | 结果缓存在 `request.context()` 里，命中则跳过 | RAG 检索：第一次算完放 context，后续轮次直接取 |
| **往 prompt 加内容** | **由单一聚合器统一拼装**，而不是各切面各自追加 | prompt 拼装聚合器（本项目采用） |
| **写外部存储** | 用唯一键 + 存在即跳过（而非无条件插入） | 入库：文档指纹（`source` + `docHash`）判重 |
| **累加计数器 / 扣减额度** | 按请求 ID 去重，或改为"最终值"语义而非"自增" | 失败计数应记"本次请求是否失败" |

### 判断方法（写代码前问自己三句话）

1. 这个切面在 `ToolCallingAdvisor` 内层吗？→ **是就假设它会被跑 N 次**
2. 它每次跑会产生新副作用吗？→ 产生就**必须幂等**
3. 幂等靠什么保证？→ **靠结构**（单一拼装者、缓存命中、唯一键），
   **不靠"记得先检查"**（那又回到靠人记）

### 为什么要有这条

本项目在阶段 6 设计 RAG 切面时发现的：RAG 若在工具循环内层且不做幂等，
**一次用户提问会触发 N 次向量检索**（每次都是一次 embedding 调用 + 一次数据库查询），
而用户的问题根本没变 —— 结果是**成本被乘了 N 倍，且没有任何报错**。

这类问题与第 ⑦ 条同源：**不是写错了代码，而是没意识到代码会被执行几次。**

## 12. 命名约定：名字必须描述本质，不得携带历史概念

**规则**：新增或重命名任何类、接口、枚举值、配置键时，必须满足下面 7 条。
**违反命名与写错代码同级** —— 名字是读代码的人唯一的入口，名字撒谎会让后续所有人基于错误前提推理。

| # | 规则 | 本项目已有的实证来源 |
|---|---|---|
| **1** | ★ **名字不得携带历史概念**。已被删除的机制不能残留在任何类名 / 配置键 / 字段名里 | 阶段 8 删除 advisor 链 → `AdvisorProperties` 与 `hagent.advisor.trace` 必须改名（保留会让配置层指向一个已不存在的概念） |
| **2** | ★ **同一个概念全链路只允许一个名字**，禁止同义异名 | 记忆的"最终答 / 写回 / append"指同一件事，代码里只应出现一个词；命名要跟着**已存在的配置前缀**走 |
| **3** | **后缀必须承载"种类"语义**：`Service`=业务编排、`Pipeline`=顺序编排、`Properties`=配置、`ModelOutput`/`Event`=数据 | HANDOFF 踩坑 #25（`*Service` 实测 3/4 在 `app/`、`*Properties` 7/10 在 `config/`） |
| **4** | ★ **名字不得撒谎**：一个类只承担一个主要职责 | 踩坑 #12（字段被赋值但无人读）；决策 26（一个切面装不下"读"与"写"两个相反位置） |
| **5** | **技术角色与能力域冲突时，跟种类走**；没有既定种类时才跟能力域 | 踩坑 #25 原文："类的种类有既定归属时跟种类走，没有时才跟能力域走" |
| **6** | ★ **产出数据的类，名字必须说清"是谁的产出"** | `Retrieved`（我们的检索产物）与 `ModelOutput`（模型的产出）来源不同，**不得塞进同一个概念名下** |
| **7** | **新增机制要同步术语表**（见下方），概念与代码名必须能双向对照 | 本项目的 `chat` / `workflow` 一度与 `CONVERSATION` / `WORKFLOW` 混用 |

### 为什么要有这条

**因为命名错误是本项目唯一一类"所有测试都会通过"的错误。**
编译通过、测试全绿、功能正确 —— 但读代码的人在名字上被误导，
于是基于错误前提做下一个决策，而**没有任何机制会拦住他**。

本项目已有的、散落在各处的同类教训：

- **配置键撒谎最贵**：`hagent.advisor.trace` 在 advisor 删掉之后仍指向一个不存在的概念，
  后来者会去搜 `Advisor` 类，然后搜不到 —— 而他不会怀疑配置键，只会怀疑自己的理解；
- **名字把"两个东西"说成"一个"**：`ConversationMemoryAdvisor` 曾经一个名字装下
  "读历史"与"写回最终答"两个**位置要求相反**的职责（决策 26），
  名字看不出这个矛盾，于是没人发现它装不下；
- **名字把"一个东西"说成"两个"**：本项目一度把 `chat` / `workflow` / `agent` 三个词
  混用于同一组概念，而其中 `agent` 的定义（harness + model）与"模式"根本不是一回事。

这三条的共同点是：**代码全对，认知错了**。
它与第 7 条同源 —— 第 7 条防的是"写一层不该存在的代码"，
第 12 条防的是"给存在的东西起一个指向别处的名字"。
两者都是**把认知错误第一次就固化下来**的那类问题，而它们都没有编译器告警。

## 13. 尽可能复用已有的概念与变量 —— 不给同一个语义造第二个名字（硬约束）

### 规则

1. **动手前先搜索，不要靠回忆**：引入新字段 / 新枚举 / 新常量 / 新方法之前，
   先在代码里 `grep` 一遍这个语义（用什么词搜？用你能想到的**中英文各一种**）。
2. **有就复用，并且调同一个定义点**：复用类型还不够，必须调用**同一处定义的逻辑**，
   而不是"照着它再写一份等价的"。
3. **真要新增，必须说清它比已有的多出了什么**。说不出来 → 就是不新增。

### 为什么要有这条

- **同一个语义两处定义，迟早会漂移**。漂移的典型表现是"某个角落的权限 / 预算 / 格式
  悄悄和别处不一样"，而它**不会报错** —— 项目里最难查的一类 bug。
- 本项目已有这条的**正例**：`AccessLevel` 同时提供
  `visibleTo(用户密级)`（逐条判定）与 `visibleLevels(用户密级)`（给 SQL 用的清单），
  后者用 `filter(visibleTo)` **派生**自前者 ——
  于是"逐条判定"和"检索过滤"**永远不可能给出不同答案**。
- 也有**反例**：`chat_message.seq`（会话内序号）与自增 `id` 并存，
  最后证明 `seq` 是个**没有任何消费者**的新概念，却带来了锁、死锁与重试（见坑 30）。

### 本次的真实例子（阶段 11 方案讨论，被当场纠正）

- 我提出："长期记忆的条目要带一个 **clearance** 字段，注入时按当前 clearance 过滤"。
- 但项目里**早就有**：`Role.clearance()` 返回 `AccessLevel`、`UserContext.clearance()`
  委托它、`AccessLevel.visibleTo(...)` 就是逐条判定。
- "clearance" 是我造的**同义词**。后果不是编译错误，而是让"密级"这件事
  看起来有**两套**（`AccessLevel` 与 clearance），后来者会去搜一个不存在的类型。
- **正解**：记忆条目**直接存 `AccessLevel`**，注入时调
  `entry.level().visibleTo(user.clearance())` —— 与检索同一条规则、同一个定义点。
- ★ 讽刺的是：我是在"提出要防一个权限漏洞"的时候，顺手造了个重复概念。
  **最容易犯这个错的时候，恰恰是你正在加新东西的时候** —— 因为注意力都在"新"上。

### 判断方法：三问

1. 这个语义的名字，在项目里搜过了吗？（`grep`，不是"我记得没有"）
2. 我起的新名字，是不是某个已有名字的**同义词**？是 → 删掉新名字。
3. 我是在调**同一个定义点**，还是复制了一份等价逻辑？复制 → 改成调用。
